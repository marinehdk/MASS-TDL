# Design Grounding Skill 设计文档

> **状态**: 设计完成,待 writing-plans
> **创建**: 2026-07-16
> **分支**: `codex/design-grounding-skill` (worktree `.worktrees/design-grounding-skill`,基于 `l3-tdl`)
> **定位**: 废弃 `spec-preflight`,新建独立前置 Skill,链路 `design-grounding → brainstorming → writing-plans → exec → verify → finish`

## 1. 问题与目标

### 1.1 现状缺陷

当前方案设计链路依赖 `superpowers:brainstorming`,它有一个根本假设:**用户是领域专家**,技能只负责提出几个问题补充。但在 MASS-TDL 深入开发中,用户对方案细节没有判断能力,导致:

- **MPC 预测时域 90s 决策**:调研确定 90s 合理,实现后问题重重。根因不是 horizon 数值选错,而是整个方案设计阶段从未显式分解 MPC 的关键技术流程(预测模型、优化问题、约束层级、求解器、参考跟踪、失败回退),也未压力测试失效边界。
- **方案无溯源**:brainstorming 提出方案但不展示来源(论文/标准/工程实践)、工程验证程度、实现风险,用户无法判别采纳与否。
- **小白失控**:当方案采用某技术(如 MPC),其内部关键流程/子模块从未与用户对齐,导致实现默认走最简版本,输出固化无法调整,用户对代码流程和业务流程完全失控。

已有的 `spec-preflight` Skill 试图解决,但产出的是官僚化路由简报而非可判别方案智能,体感不好。

### 1.2 目标

构建 `design-grounding` Skill,让**非专家**也能产出有溯源、有压力测试、有技术分解完整性、有风险量化、有技术语义固化的可判别工程方案。核心机制:用"调研显式化专家判断"代替"假设你已有专家判断"。

### 1.3 范围

- **服务领域**: MASS-TDL / 海事(COLREGs、MPC、ODD、ROS2 DDS 等)。绑定 TDL 上下文与海事术语。
- **输入**: 用户的需求描述 + 目标模块(M1-M8)。
- **输出**: 方案包(Solution Pack),交付 `brainstorming` 作为工程细节设计的强制输入。
- **不负责**: 正式 Spec 写作(brainstorming 负责)、实现计划(writing-plans 负责)、TDL subagent 路由(AGENTS.md 在 brainstorming 之后管理)。

## 2. 身份、定位与核心机制

### 2.1 身份与定位

| 项 | 定义 |
|---|---|
| **名字** | `design-grounding`(设计接地/落地) |
| **定位** | 独立前置 Skill,在 `brainstorming` 之前。链路:`design-grounding → brainstorming → writing-plans → exec → verify → finish`。废弃 `spec-preflight`。 |
| **一句话** | 让非专家也能产出有溯源、有压力测试、有技术分解完整性、有风险量化的可判别工程方案。 |
| **核心解决** | brainstorming 默认你是专家;本 Skill 用"调研显式化专家判断"代替"假设你已有专家判断"。 |

### 2.2 三个核心机制(贯穿全部 6 步)

#### 机制 A:决策树状态文件(Decision Tree Log)

单个 Skill 运行期间维护一份持续演进、**落盘**的决策树状态,以追加式 LOG 形式的 Markdown 文件保存。

| 项 | 说明 |
|---|---|
| **为什么落盘** | 2 个月后用户和 agent 仍能完整溯源"当时为什么这么决策、证据从哪来、弃用了什么"。不落盘 = 设计细节必然遗忘。 |
| **格式** | 追加式 LOG Markdown,每条决策带时间戳、阶段、证据引用、弃用理由。人和 agent 都能直接阅读。 |
| **存储位置** | `docs/superpowers/design-logs/YYYY-MM-DD-<topic>-design-log.md`(与 spec/plan 同目录族,便于关联) |
| **结构** | 注册表(当前态,可变快照)+ 演进日志(历史态,append-only 时序)。详见第 3 节文档标准。 |

#### 机制 B:证据权重与重构支持

证据按权威性分层,**代码库/现有设计不是零权重**——它们是合法证据源,尤其在重构评审场景下是主要依据。技能同时支持两种模式:

| 模式 | 触发 | 证据权重 |
|---|---|---|
| **新建设计(Greenfield)** | 全新功能,无现有实现 | 外部权威(NLM/web)为主,代码库用于理解业务约束 |
| **重构评审(Redesign)** | 已有实现/设计待评审查漏补缺 | 现有代码/设计是主要证据之一,外部权威用于验证/补强/纠偏 |

判定规则:技能在 Step1 检测目标模块是否已有实现/设计。已有 → 重构模式,以"评审现有决策点 + 发现遗漏决策点 + 外部验证"为主;无 → 新建模式。两种模式都避免全盘否定已有成果。

证据权威性分层(所有模式通用):
- `DOMAIN_EVIDENCE`(规则/标准/论文/已建立工程实践):权重最高
- `PROJECT_FACT`(当前代码/配置/测试/trace):权重高,但仅证明"当前是这样",不证明"应该这样"
- `DOCUMENTED_INTENT`(权威设计文档陈述):中
- `ASSUMPTION`/`UNKNOWN`:必须显式标注,不得伪装成定论

#### 机制 C:技术分解(Technique Decomposition)

| 项 | 定义 |
|---|---|
| **触发** | 当一个决策点的答案是"采用某技术/算法/框架"(MPC、NLP、EKF、COLREGs FSM、IvP 仲裁……)时,立即触发分解 |
| **做什么** | 把该技术的**关键内部流程/子模块**分解成独立决策点,逐一对齐。不可停留在"用 MPC"这一层 |
| **为什么** | 每个内部组件都是决定实现成败的细节;不分解 → 实现默认走最简版 → 输出固化无法调整 → 小白对代码流程和业务流程完全失控 |
| **判定标志** | 决策点答案形态是"采用某技术"而非"选某个数值/架构选择" |
| **示例(MPC)** | "用 MPC" → 必须分解为:①状态量/控制量 ②预测模型 ③目标函数 ④约束层级(硬约束/软约束+slack) ⑤求解器 ⑥参考跟踪 ⑦失败回退。每一项独立对齐 |
| **落盘** | 分解出的子模块全部进入机制 A 的决策树日志,各自成为独立决策点 |

## 3. 决策树日志文档标准

决策树日志要同时满足"2 个月后能溯源"和"agent 能稳定解析索引",采用**注册表(当前态)+ 演进日志(历史态)**双层结构:注册表是权威索引(可变,反映最新状态),演进日志是 append-only 时序记录(解释每次状态怎么变的)。

### 3.4 排版硬规则

1. **ID 唯一且稳定**:一旦分配永不复用、不重编号。删除项保留 ID 标记 `~~废弃~~`。
2. **双层一致**:演进日志每次状态变更必须更新对应注册表。注册表是索引,演进日志是证据链,两者 ID 对齐。
3. **表格固定列**:每个注册表列序固定(3.3 节即标准),新增字段加到最右,不插中间。
4. **三置信度分列**:`检索置信 / 来源权威 / 场景适用`,不允许合并成一列模糊描述。
5. **引用闭环**:正文出现 `[RNN]` → 参考文献必须有对应条目;注册表"引用"列不允许裸文字描述,必须 `[RNN]`。
6. **时序区块**:每个 Step 一个二级标题,带时间戳,内部按事件列,只追加不删改历史(改裁决 = 新增 VR 行 + 更新 DP 状态,不抹掉旧 VR)。
7. **状态枚举固定**:决策点状态只用 `未决|调研中|已裁决|暂停(EXTERNAL_CONFIRMATION_REQUIRED)`;证据适用性只用 `高|中|低|不适用`。

## 4. 六步流程详解

三个机制(A 决策树日志 / B 证据权重与模式 / C 技术分解)贯穿全部 6 步。每步有决策门,满足才进下一步。决策树日志全程追加。

### 流程总览

```
Step1 行业调研·发现决策点 ──触发机制C技术分解──┐
   │  产出: 决策点列表 + 盲区初判              │
   ▼                                          │
Step2 grilling 压力测试 ◄────────────────────┘ 对每个决策点/子模块
   │  产出: 盲区清单 + grilling记录            │ 分解后逐个压力测试
   ▼
Step3 自主深度调研(Web+NLM) 针对盲区
   │  产出: 证据矩阵(对比矩阵式)
   ▼
Step4 汇总分析·推荐方案
   │  产出: 推荐方案 + 理由 + 弃用方案
   ▼
Step5 DESIGN-IT-TWICE 方案对比
   │  产出: 决策卡片
   ▼
Step6 定义术语表 + 固化技术规约 + 产出方案包
   │  产出: 方案包(术语表+技术规约表+决策卡片+证据矩阵+验收边界)
   ▼
交给 brainstorming(方案包注入,工程细节设计器)
```

### 4.1 Step 1:行业调研 · 发现决策点

**目标**:不预设用户知道哪些决策维度。先快速扫描行业/研究现状,从文献/实践中自动提取这个需求领域里"业界在吵哪些关键决策",变成决策点交给后续 grilling。同时判定新建/重构模式(机制B)。

**执行**:

1. **模式判定**(机制B):用 codegraph + 读现有代码/设计文档,检测目标模块是否已有实现/设计。
   - 已有 → **重构模式**:现有代码/设计是主证据之一,目标是"评审查漏补缺"
   - 无 → **新建模式**:外部权威为主
   - 模式写入决策树日志首条

2. **快速调研**(限时、广度优先):
   - NLM `nlm-research --depth fast` 扫描相关笔记本(`colav_algorithms` / `ship_maneuvering` / `maritime_regulations` / `safety_verification`),提取该领域的标准决策维度
   - Web 扫描:关键词 = 需求 + "design decisions / trade-offs / pitfalls / lessons learned / comparison",目标是找"业界对这个问题的决策点共识与争议",不是找具体答案
   - 代码库:仅理解业务约束(机制B)——现状、上下游接口、已有成果

3. **提取决策点**:把调研发现的决策维度转成决策点,写入决策树日志。每个决策点标注:
   - `id` / 描述 / 类型(架构|算法|约束|阈值|接口|技术)
   - 来源(哪条调研发现的)
   - 状态:未决

4. **技术分解触发**(机制C):对每个类型为"技术"的决策点(答案形态是"采用某技术"),立即分解:
   - 从调研/NLM 获取该技术的标准内部结构(如 MPC = 预测模型 + 优化问题 + 约束处理 + 求解器 + 参考跟踪 + 失败回退)
   - 每个内部子模块变成独立决策点,挂到父决策点下
   - 不可停留在"用 MPC"这一层

**决策门(进 Step2 的条件)**:
- ✅ 至少识别出该领域的主干决策维度(非空)
- ✅ 所有技术型决策点已触发技术分解,子模块全部成为独立决策点
- ✅ 决策树日志已含决策点列表 + 模式判定
- ❌ 若调研结果为空或过于肤浅 → 回退重调,或标注 `EXTERNAL_CONFIRMATION_REQUIRED` 暂停

**输出到日志**:`决策点列表`(含技术分解树)+ `模式判定` + `调研来源清单`

**分阶段输出形态**:此阶段以注册表形式记录决策点,向用户展示决策点清单(含技术分解树)请求确认。

### 4.2 Step 2:grilling 压力测试

**目标**:对每个决策点(含技术分解出的子模块)逐个压力测试,用 Matt Pocock grilling 的多视角追问,逼出每个决策点的失效边界、用户真实需求场景、用户的知识盲区。

**执行**:

1. **逐决策点 grilling**(一个一个来,不批量)。对每个决策点施加三视角追问:
   - **专家视角**:这个决策在领域标准/论文里公认怎么做?有什么前置条件?
   - **新手视角**:为什么不是最简单的做法?为什么不是现状(重构模式)?
   - **悲观视角**:这个决策选错了/缺失了会怎么失效?边界条件是什么?

2. **记录需求场景**:grilling 过程中,用户描述的真实运营/操作场景(如"船舶在受限水域低速大转向角时")必须记录——这是后续验收边界的依据。

3. **采集盲区**(关键产出):当用户对某追问无法判断/回答时,**记录为盲区,不逼用户猜**。每条盲区标注:
   - 问题
   - 为什么用户答不了(知识空白 / 需要领域权威 / 需要实验数据)
   - 调研优先级(高/中/低,由该盲区对实现成败的影响决定)

4. **技术分解子模块的专项 grilling**:对机制C分解出的每个子模块,悲观视角必须追问"这个子模块如果被默认实现成最简版,会导致什么?"——这正是 M5 MPC 返工的根因预防。

**决策门**:
- ✅ 每个决策点都经过三视角追问
- ✅ 所有技术分解子模块都经过"默认最简版会失效什么"追问
- ✅ 盲区清单非空时,每条都有调研优先级
- ✅ 需求场景已记录
- ❌ 若仍有决策点未经过压力测试 → 不进 Step3

**输出到日志**:追加 `盲区清单` + `grilling 记录(三视角)` + `需求场景记录`

**分阶段输出形态**:Step2 用 **grilling 记录 + 裁决**形态展示给用户。

### 4.3 Step 3:自主深度调研(Web + NLM)

**目标**:针对 Step2 采集的盲区,自主深度调研,不把技术问题抛回给用户。目标是把盲区转成带来源、带置信度、带适用性评估的证据。

**执行**:

1. **按优先级调研**:高优先级盲区先调。每个盲区:
   - 先 NLM `nlm-ask` / `nlm-research --depth fast` 查 curated 笔记本
   - 不够或过时 → Web 深搜(论文/标准/工程实践/已知失效案例)
   - 仍不够 → NLM `nlm-research --depth deep`(每个 topic 至多一次,需理由)
   - 最后才是 Web 通用检索兜底

2. **盲区转证据**:每条调研结果必须回答原盲区问题,并标注:
   - 来源类型(NLM / web / 代码库)
   - 引用 `[RNN]`
   - NLM 检索置信度 ≠ 来源权威性 ≠ 本场景适用性(三者分开评)
   - 适用性:这个证据对当前具体场景是否成立(如论文用全速域,本场景是低速大角,适用性要打折)

3. **可并行**:多个高优先级盲区可并行调研(用通用 subagent 并行,纯流程技能在此处唯一用 subagent 的场景)。subagent 只返回证据,**不做方案裁决**——裁决永远在主线程。

4. **填充证据矩阵**:把所有证据填入决策树日志的证据矩阵,按决策点归组。

**决策门**:
- ✅ 每个盲区都有对应证据或显式标注 `UNKNOWN`/`EXTERNAL_CONFIRMATION_REQUIRED`
- ✅ 证据的三类置信度(检索/权威/适用)分开标注
- ✅ 技术分解子模块的盲区全部覆盖(机制C)
- ❌ 若关键盲区无证据且无法调研 → 标 `EXTERNAL_CONFIRMATION_REQUIRED` 暂停,问用户是否接受该未知继续

**输出到日志**:追加 `证据矩阵`(按决策点归组,含三类置信度)

**分阶段输出形态**:Step3 用 **对比矩阵式**展示不同置信度的方案/证据。

### 4.4 Step 4:汇总分析 · 推荐方案

**目标**:把 Step1-3 累积的决策点、盲区、证据综合成一份带推荐的方案分析,让小白能判别。这不是定稿(Step5 还要 DESIGN-IT-TWICE 对比),但每条推荐必须有证据链和风险量化。

**执行**:

1. **逐决策点综合**(按 DP 编号顺序):
   - 汇总该决策点的所有证据 `[RNN]`、grilling 三视角结论、技术分解子模块状态
   - 给出**初步推荐**及理由(证据链形式:`[R1][R2] 一致 → 推荐 X`)
   - 列出该决策点的**备选/弃用方案**,每条弃用必须写理由(引用 `[RNN]` 或盲区标注)

2. **技术分解完整性校验**(机制C专项):
   - 对每个 `TD-NN`,检查分解出的所有子模块决策点是否都已综合
   - **任一子模块留有未闭环盲区 → 该技术整体标 `DECOMPOSITION_INCOMPLETE`,不允许进 Step5 对比**。预防 M5 MPC 返工的硬门
   - 输出"技术分解就绪度"摘要:每项子模块 `[✓已裁决 | ○调研中 | ✗盲区未闭环]`

3. **风险量化**:对每个推荐方案标注:
   - 实现风险(高/中/低)+ 具体风险来源
   - 失效边界(在什么输入/条件下会失效)
   - 验证需求(用什么测试/场景能证明它成立或暴露失效)

4. **冲突标注**:当证据互相矛盾(如 NLM 说 A,web 说 B),显式记录为冲突,不投票抹平,留到 Step5 用 DESIGN-IT-TWICE 对比解决。

**决策门**:
- ✅ 所有决策点都有初步推荐 + 证据链 + 备选/弃用理由
- ✅ 所有技术分解的子模块决策点状态明确(无遗漏);未闭环的标 `DECOMPOSITION_INCOMPLETE`
- ✅ 每个推荐有风险量化 + 失效边界 + 验证需求
- ❌ 若存在 `DECOMPOSITION_INCOMPLETE` 且子模块盲区可调研 → 回 Step3 补调;不可调研 → 标暂停问用户

**输出到日志**:追加到演进日志 `Step4`;更新注册表 `0.6 裁决注册表`(初步推荐写入,标记 `初稿`)+ `0.7 备选/弃用方案`

### 4.5 Step 5:DESIGN-IT-TWICE 方案对比

**目标**:借鉴 Matt Pocock `codebase-design/DESIGN-IT-TWICE`,对关键决策点做并行方案对比,而非单一选择。逼出"如果不这么做会怎样",防止默认走最简版。

**执行**:

1. **选定对比对象**:不所有决策点都做 DESIGN-IT-TWICE(太重)。选择标准:
   - 技术分解的整体技术方案(如"MPC 整体建模方式"作为一组对比)
   - 影响实现成败的核心决策点(风险高、证据冲突、子模块多)
   - 跳过:低风险、证据一致、单一数值的决策点(直接采纳 Step4 推荐)

2. **为每个对比对象设计 2-3 个竞争方案**:每个方案必须是完整自洽的(覆盖该技术/决策点的所有子模块),不允许只比局部。例如 MPC 对比要完整覆盖:预测模型 + 优化问题 + 约束层级 + 求解器 + 回退,三个方案在这五维上各有不同。

3. **并行对比**(此处可用通用 subagent 并行,每方案一个,纯流程技能第二次用 subagent 的场景):每个 subagent 深化一个方案,返回该方案的完整刻画。subagent 不做裁决。

4. **多维对比**——核心产出。每个对比对象出一张**决策卡片**,维度固定:
   ```
   ┌─ 方案 A: <名称> ─────────────────────────────┐
   │ 来源      │ [R1]... [R2]...                    │
   │ 工程验证  │ nav2 生产✓ / 仅论文✗ / 仅本项目✗   │
   │ 技术分解  │ 预测模型✓ 优化✓ 约束✓ 求解✓ 回退✓ │
   │ 失效边界  │ >X 时求解超时(见 SC-NN)           │
   │ 实现风险  │ 中(实时边界紧)                    │
   │ 可测性    │ SIL 场景 SC-NN 可证                │
   │ 推荐度    │ ★★★★☆                            │
   └──────────────────────────────────────────────┘
   ```

5. **裁决**:对每个对比对象给出最终采纳方案 + 弃用方案及理由。裁决必须解释:为什么采纳方在证据/工程验证/技术分解完整性/失效边界上优于弃用方。

**决策门**:
- ✅ 所有关键决策点/技术方案都经过 DESIGN-IT-TWICE 或显式标注"低风险直接采纳"
- ✅ 每张决策卡片维度完整(七维全填)
- ✅ 裁决有证据链理由,弃用方案有明确弃用理由
- ❌ 若两方案证据相当、无法用证据裁决 → 标记为"运营/风险取舍",用场景化问题问用户(只在此处打断用户)

**输出到日志**:追加到演进日志 `Step5`;更新 `0.6 裁决注册表`(最终裁决覆盖初稿)+ `0.7 备选/弃用方案`;决策卡片全文进演进日志。

**分阶段输出形态**:Step5 用 **决策卡片**形态展示最终对比结论。

### 4.6 Step 6:定义术语表 + 固化技术规约 + 产出方案包

**目标**:
1. 固定专业术语和概念(防术语漂移)。
2. 固化物理量单位、坐标系、符号约定等技术语义(防实现语义不一致)。
3. 打包方案包,作为 brainstorming 强制输入。

**执行**:

1. **术语表**:从全部决策点、技术分解、证据中提取专业术语,每个术语:
   - 定义(引用权威来源 `[RNN]`)
   - 在本方案中的具体含义(区别于通用定义)
   - 反义词/边界(它**不是**什么,防止混淆)
   - 关联决策点 `[DP-NN]`

2. **技术规约表(Technical Specification)**——方案包独立组件。从全部决策点、技术分解、证据中提取所有技术语义,逐项固化:

   | 规约类别 | 必须锁定的内容 | 示例(MASS-TDL) |
   |---|---|---|
   | **坐标系** | 使用的坐标系及转换关系:全局(WGS84/UTM)、当地(ENU/NED)、船体(body frame);各坐标系原点、轴定义、转换链 | world=ENU, body=x-forward/y-port, 旋转 ψ逆时针正 |
   | **物理量单位** | 每个物理量的标准单位,接口/公式/阈值统一 | u=kn, ψ=deg, ROT=deg/s, 距离=m, 时间=s |
   | **符号约定** | 角度正负向、旋转方向、参考零点 | 舵角右舷正;ROT 右转正;艏向 0=正北顺时针 |
   | **时序约定** | 时间戳基准、频率、相位关系 | stamp=ROS2 steady, M5@1-4Hz, L4@10Hz |
   | **数值边界** | 关键量的物理可行域、饱和、无效值表示 | u∈[0,30]kn;无效=-1;NaN=故障 |
   | **接口语义** | 关键输入输出的字段含义、缺失/无效处理 | psi_cmd 缺失→保持上一值 |

   每条规约必须:
   - 标注**来源权威** `[RNN]`(标准/规则/工程实践)或显式 `DESIGN_DECISION`(本方案决定,理由附上)
   - 标注**关联决策点** `[DP-NN]` 和**关联接口**
   - 标注**与现有代码的差异**(重构模式下):若现状与规约不一致,显式记录偏差 + 是否需修正

3. **方案包组装**(交付 brainstorming)。方案包固定组件(八项):
   1. 术语表
   2. 技术规约表
   3. 决策卡片集(Step5 最终裁决)
   4. 证据矩阵(Step3 完整溯源)
   5. 技术分解完整树(所有 `TD-NN` 及子模块裁决)
   6. 弃用方案及理由
   7. 需求场景 + 验收边界
   8. 已知冲突与未闭环盲区

4. **方案包契约**(brainstorming 权限边界):
   - ✓ 可做:工程细节设计(架构/组件/数据流/错误处理/测试),在已裁决方案内的优化拔高
   - ✗ 不可做:推翻已裁决核心方案(决策卡片中的裁决),除非发现**新矛盾证据**(此时必须回到 design-grounding)
   - ✗ 不可做:重新提出已弃用方案(ALT 注册表中的)
   - ✗ 不可做:擅自修改技术规约表中的单位/坐标系/符号约定(需改则回 design-grounding 重新裁决)

5. **移交**:
   - 方案包保存为独立文件:`docs/superpowers/specs/YYYY-MM-DD-<topic>-solution-pack.md`(与日志同目录族)
   - 决策树日志标状态 `已交付 brainstorming`
   - 调用 `superpowers:brainstorming`,把方案包作为权威输入注入

**决策门**:
- ✅ 术语表覆盖所有专业术语
- ✅ 技术规约表覆盖所有出现的坐标系、单位、符号、时序、数值边界(无遗漏,无歧义)
- ✅ 方案包八组件齐全
- ✅ 方案包契约明确写入
- ✅ 所有 `DECOMPOSITION_INCOMPLETE` 已闭环或显式标暂停
- ❌ 技术规约表有未确定项 → 不交付

**输出到日志**:追加 `Step6`;日志头标 `已交付 brainstorming`;方案包独立成文;技术规约表同时写入决策树日志注册表 `0.8 技术规约 [TS]`。

**分阶段输出形态**:Step6 产出**方案包**(八组件完整文档),作为交付物展示给用户审核,并在用户接受后注入 brainstorming。

## 6. 与 brainstorming 的衔接契约

用"方案包注入"解决 brainstorming 默认用户是专家的问题。衔接点在 brainstorming 检查清单的第 1 步(探索项目上下文)和第 3 步(提问):

| brainstorming 原行为 | design-grounding 注入后的行为 |
|---|---|
| 检查项目状态 | **必须先读方案包**(solution-pack.md)和决策树日志 |
| 默认你是专家,提问补充 | 方案包已含专家判断(证据溯源),**不再问技术决策问题** |
| 提出 2-3 方案对比 | **已裁决方案不可推翻**,只在已裁决方案内做工程细节优化 |
| 写 Spec | Spec 必须包含方案包的技术规约表和术语表,不得修改已裁决内容 |

**落地方式**(不修改 superpowers 原文件,通过 SKILL.md 指令约束):
- design-grounding 的 SKILL.md 移交指令明确写:"调用 brainstorming 时,把方案包路径作为第一输入,并声明:本方案的核心技术决策已通过 design-grounding 裁决,brainstorming 负责工程细节设计,不得推翻已裁决方案/重提弃用方案/修改技术规约,除非发现新矛盾证据则回炉 design-grounding。"
- 方案包文件首部写明同样的契约,使 brainstorming 读到时即知边界。

**回炉机制**:brainstorming 若在工程细节设计中发现新矛盾证据(如实现某组件时发现已裁决方案的约束不可行),必须暂停并回到 design-grounding,带着新证据重跑受影响的决策点。不可在 brainstorming 里私自改方案。形成闭环:
```
design-grounding → brainstorming ──(新矛盾证据)──> 回 design-grounding
                          │
                          └─(无矛盾)──> writing-plans
```
