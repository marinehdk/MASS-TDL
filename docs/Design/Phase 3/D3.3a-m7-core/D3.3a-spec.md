## 4. 6 类硬约束设计

### 4.1 约束清单与设计原理

6 类硬约束是 M7 Checker 的**确定性安全检查器**，在 < 10ms 内对 Doer 输出进行交叉验证。每类约束的检测逻辑极简（单函数 ≤ 40 行），不依赖 Doer 内部状态。

| 编号 | 约束名称 | 输入信号 | 检测逻辑 | 违反响应 | SIL 关联 |
|---|---|---|---|---|---|
| **HC-1** | CPA 一致性交叉验证 | M2 WorldState.CPA + M5 AvoidancePlan.DCPA | `|CPA_doer - CPA_checker| / CPA_checker > 0.10` → VIOLATION | MRM-03 紧急转向 | SIF-01 |
| **HC-2** | COLREGs 规则-几何一致性 | M6 COLREGsConstraint.rule + M5 AvoidancePlan.heading_change | 规则要求转向但几何方向相反 → VIOLATION | MRM-01 减速维持航向 | SIF-02 |
| **HC-3** | 模块心跳 watchdog | 各模块最新消息时间戳 | `ΔT > expected_period × 1.5` 连续 > 3 次 → CRITICAL | 降级至 D2 + 触发 MRM-01 | SIF-01 |
| **HC-4** | IEC 61508 SIL 2 DC≥90% | M7 内部 DC 自检 | 周期 DC 自检结果 < 90% → VIOLATION | 降级至 D2 + 触发 MRM-01 | SIF-01 |
| **HC-5** | 速度限制合规 | M5 AvoidancePlan.speed + Capability Manifest.speed_max(U) | `speed > speed_max × 1.05` → VIOLATION | MRM-01 减速至 safe_speed | SIF-03 |
| **HC-6** | ROT 限制合规 | M5 AvoidancePlan.rot + Capability Manifest.rot_max(U) | `|rot| > rot_max × 1.05` → VIOLATION | MRM-03 限制转艏率 | SIF-03 |

### 4.2 HC-1 CPA 一致性交叉验证（±10%）

**检测目的**：验证 M2 WorldModel 报告的 CPA 与 M5 Planner 使用的 DCPA 一致。不一致表明 Doer 内部计算链存在错误或数据陈旧。

**算法**（伪代码，≤ 40 行）：

```cpp
// 输入：M2 CPA, M5 DCPA, M7 独立计算的 CPA
// 输出：一致性判定 + 违反标志
struct CpaConsistencyResult {
  bool consistent;
  float deviation_pct;  // |CPA_M2 - CPA_M7| / CPA_M7 × 100%
  std::string violation_reason;
};

CpaConsistencyResult check_cpa_consistency(
    float cpa_m2,      // 来自 M2 WorldState
    float dcpa_m5,     // 来自 M5 AvoidancePlan
    float cpa_m7,      // M7 独立差分计算
    float threshold)   // 默认 0.10 (10%)
{
  // Step 1: M7 独立计算 CPA（基于当前位置 + 速度矢量差分）
  //         使用极简匀速直线模型（与 M5 Mid-MPC 无关）
  // Step 2: 三方交叉验证
  //   - |CPA_M2 - CPA_M7| / max(CPA_M7, ε) ≤ threshold
  //   - |DCPA_M5 - CPA_M7| / max(CPA_M7, ε) ≤ threshold
  // Step 3: 违反 → Safety_AlertMsg (severity=CRITICAL, recommended_mrm=MRM-03)
  //         同时记录 ASDR（含三方 CPA 值 + 时间戳）
}
```

**关键设计决策**：
- M7 使用**独立极简 CPA 计算**（匀速直线模型），不与 M5 Mid-MPC 共享预测模型
- ±10% 阈值基于 Veitch 2024 TMR 60s 实证基线 [R4]：CPA 估算误差 < 10% 时，TMR 不确定性可控
- 违反时选择 MRM-03（紧急转向）而非 MRM-01（减速），因为 CPA 不一致表明碰撞风险评估不可信
- **独立性保证**：M7 仅使用 M2 WorldState 中的 position + velocity 字段，不依赖 M2 的 CPA 计算逻辑

### 4.3 HC-2 COLREGs 规则-几何一致性

**检测目的**：验证 M6 COLREGs Reasoner 输出的规则与 M5 Planner 输出的几何动作在方向上一致。例如：M6 判定"目标船为让路船（Rule 15），本船应保向保速"，但 M5 输出 heading_change = +30° → 不一致。

**检测矩阵**（极简真值表，≤ 30 行）：

| M6 Rule 输出 | M5 期望几何 | 违反条件 |
|---|---|---|
| Rule 13 Overtaking | heading_change ≈ 0（保向），或转向远离 | heading_change 朝向来船方向 |
| Rule 14 Head-On | heading_change 向右（starboard） | heading_change 向左（port） |
| Rule 15 Crossing (give-way) | heading_change 向右（starboard，从右舷来船） | heading_change 向左 |
| Rule 15 Crossing (stand-on) | heading_change ≈ 0（保向保速） | heading_change > 5° |
| Rule 16 Give-way action | heading_change > 15°（大幅避让） | heading_change < 5°（几乎无动作） |
| Rule 17 Stand-on action | heading_change < 5°（保持） | heading_change > 10° |
| MRM 触发状态 | heading_change = 0（紧急） | 任何非零动作 |

**M7 不解析 M6 rule_violations 详情**：M7 仅检查 M6 输出的 `rule_applied` 枚举 + M5 的 `heading_change` 方向一致性。不重新推理 COLREGs 规则细节（保持 Checker 简化性）。**违反时**：触发 MRM-01（减速维持航向）— 因为 COLREGs 推理不可信时最安全动作是减速。

### 4.4 HC-3 模块心跳 watchdog

**检测目的**：监控 M1–M6、M8 共 7 个 Doer 模块的心跳，检测模块崩溃或通信中断。

**设计参数**：

| 模块 | 期望周期 | timeout（× 1.5） | 容忍次数 | 实际响应 |
|---|---|---|---|---|
| M1 ODD Manager | 1000 ms (1 Hz) | 1500 ms | 3 → 4th miss = CRITICAL | 4500 ms |
| M2 World Model | 250 ms (4 Hz) | 300 ms | 3 → 4th miss = CRITICAL | 900 ms |
| M3 Mission Manager | 5000 ms (0.2 Hz) | 7500 ms | 2 → 3rd miss = CRITICAL | 15000 ms |
| M4 Behavior Arbiter | 500 ms (2 Hz) | 750 ms | 3 → 4th miss = CRITICAL | 2250 ms |
| M5 Tactical Planner | 1000 ms (1 Hz) | 1500 ms | 3 → 4th miss = CRITICAL | 4500 ms |
| M6 COLREGs Reasoner | 500 ms (2 Hz) | 750 ms | 3 → 4th miss = CRITICAL | 2250 ms |
| M8 HMI Bridge | 100 ms (10 Hz) | 150 ms | 3 → 4th miss = CRITICAL | 450 ms |

**3-miss 阈值的合理性论证**：

| 论证维度 | 分析 |
|---|---|
| 架构初始值 | 架构 §11 未明确规定精确阈值；3-miss 是基于 Veitch 2024 TMR ≥ 60s 实证的工程判断——单次消息丢失（ROS2 QoS 可靠传输下概率 < 10⁻⁶）不代表模块失效，但连续 4 次丢失表明通信链路或模块进程故障 |
| 最坏情况响应时间 | M2（4 Hz, 300ms timeout × 4 = 900ms）< TMR 60s × 保守系数 0.02 = 1.2s → 有充足时间在 MRC 前完成安全响应 |
| 误报抑制 | 3-miss 在 7 模块独立监控下，随机误报概率 ≈ P_single⁴ × 7 ≈ (10⁻⁶)⁴ × 7 ≈ 10⁻²⁴，可忽略 |
| HAZID 校准 | 3-miss 为初始值，FCB 实船试航（2026-06 起）后根据实际 DDS 通信可靠性数据校准 |

**与现有 WatchdogMonitor 的关系**：现有 `iec61508::WatchdogMonitor` 已实现 MonitoredModule 枚举（kM1–kM6, kM8）+ `WatchdogConfig`（timeout_ms × 1.5 + tolerance_count = 3）。本任务在现有框架上补充 HC-3 约束集成。

**违反时响应**：
- 单模块 CRITICAL：降级至 D2 + 触发 MRM-01（减速维持航向）
- 多模块（≥ 2）同时 CRITICAL：立即 MRC + 触发 MRM-02（停车）+ 通知 ROC 介入
- M7 自身 watchdog 由 X-axis Checker 独立监控（频率 1 Hz），不在本约束范围

### 4.5 HC-4 IEC 61508 SIL 2 DC≥90%

**检测目的**：M7 周期自检诊断覆盖率（Diagnostic Coverage），确保 SIL 2 核心安全路径的 DC ≥ 90%。

**自检项**：

| 自检项 | 检测方法 | 周期 | 目标 DC 贡献 |
|---|---|---|---|
| RAM 完整性 | 预分配内存区域的 CRC-32 校验 | 每 250ms | 99% |
| 程序计数器 | 窗口 watchdog（独立时基）+ 逻辑序列检查 | 每 100ms | 95% |
| 输入数据完整性 | M2/M5/M6 消息 CRC + 时间戳新鲜度 | 每消息 | 99% |
| 输出数据完整性 | Safety_AlertMsg 回读校验（M7 发布后订阅自身消息比对） | 每消息 | 99% |
| ALU 运算 | 预定义测试向量周期执行（如 CPA 计算验证） | 每 1000ms | 90% |
| 控制流 | 关键路径签名检查（每个 main_loop 周期计算执行路径 hash，比对预期值） | 每 250ms | 90% |

**DC 聚合公式**：

```
DC_total = 1 - Π(1 - DC_i × w_i)  其中 w_i = 子项权重（均分）
目标 ≥ 90%
```

**违反时响应**：DC < 90% → M7 自身降级至 D2 + 触发 MRM-01。此为 Fail-Safe 行为（M7 宁可错误降级，不可在 DC 不足时继续运行）。

### 4.6 HC-5 速度限制合规

**检测目的**：验证 M5 Planner 输出速度不超过 Capability Manifest 定义的速度上限（含船型 + 当前工况安全系数）。

**检测逻辑**：

```cpp
// 输入：M5 AvoidancePlan.speed, M1 ODD_State.current_speed_limit
// 输出：合规判定
// speed_limit 来源：Capability Manifest.speed_max(U) × ODD_safety_factor
//   ODD-A (开阔水域): safety_factor = 1.0
//   ODD-B (港口): safety_factor = 0.7
//   ODD-C (能见度受限): safety_factor = 0.5
//   ODD-D (越界): safety_factor = 0.3
```

**违反时响应**：触发 MRM-01（减速至 safe_speed = 4 kn）。**注意**：M7 不注入速度指令到 M5，而是通过 Safety_AlertMsg → M1 仲裁 → M5 执行 MRM-01 减速。

### 4.7 HC-6 ROT 限制合规

**检测目的**：验证 M5 Planner 输出转艏率不超过 Capability Manifest 定义的 ROT 上限。

**检测逻辑**：

```cpp
// 输入：M5 AvoidancePlan.rot, M1 Capability Manifest rot_max(U)
//        U = 当前船速
// 输出：合规判定
// rot_max(U) 来自 Capability Manifest 速度相关查表
// 违反条件：|rot| > rot_max(U) × 1.05（5% 容差）
```

**违反时响应**：触发 MRM-03（紧急转向），但限制转艏率 = 0.8 × rot_max(U)（来自 §11.6 MRM-03 参数）。同样通过 M1 仲裁链路下发。

### 4.8 执行线程结构设计决策

**决策问题**：6 类硬约束的独立执行线程结构 vs 单循环（如何保证时序？）

**方案 A：独立线程每约束**（每个 HC 一个 `std::thread` + lock-free queue）
- 优点：天然并行，各自独立超时
- 缺点：线程间同步复杂；资源开销大（6 线程 × 栈 64KB = 384KB）；MISRA-C++ 禁动态线程创建；违反 PATH-S "简单优先"原则

**方案 B：单循环顺序执行**（main_loop 250ms 周期内顺序调用 6 个 check 函数）
- 优点：实现极简；无同步开销；PATH-S 合规（单线程 MutuallyExclusive callback group）
- 缺点：6 约束顺序执行需满足 < 10ms 累积延迟
- **验证**：单约束执行时间 < 0.5ms → 6 × 0.5 = 3ms << 10ms ✅

**方案 C：混合（单循环 + 关键约束提前）**（本设计推荐）
- main_loop 250ms 周期，但在接收到 M5 AvoidancePlan 消息时**立即触发** HC-1/HC-2/HC-5/HC-6（事件驱动，< 10ms）
- HC-3（watchdog）和 HC-4（DC 自检）在 250ms 周期定时执行
- 优点：关键约束（与轨迹相关）获得事件级响应；watchdog/DC 自检独立周期；总延迟可控

**决策：方案 C（混合架构）**

**理由**：
1. HC-1 (CPA)、HC-2 (COLREGs)、HC-5 (速度)、HC-6 (ROT) 与 M5 输出直接相关 → 事件驱动
2. HC-3 (watchdog) 依赖周期心跳检测 → 定时器驱动
3. HC-4 (DC 自检) 依赖硬件周期自检 → 定时器驱动
4. 全体约束仍运行在 `cb_group_main_`（MutuallyExclusive），无并发问题
5. 最坏延迟：事件驱动约束 < 2ms（CPA 计算 + 查表）+ watchdog 评估 < 0.5ms + DC 自检 < 5ms → 总计 < 8ms << 10ms ✅

### 6.5 DC% 估算方法（v0.1）

复用 D2.7 §5.5 四档专家判断法：

| DC% 范围 | 定义 | v0.1 依据 |
|---|---|---|
| ≥ 99% | 自动检测，每次使用前 | 运行时 CRC / watchdog heartbeat |
| 90–98% | 自动检测，周期 < 1s | 周期性自检 + 消息时间戳验证 |
| 60–89% | 自动检测，周期 1–10s | 状态一致性检查 |
| < 60% | 人工/外部检测 | 日志审计 / X-axis Checker 外部监控 |

> **IEC 61508-2 要求**：SIL 2 核心路径（HFT=0）须 DC ≥ 90%。**M7 作为 Checker**，HFT=1 架构（M7 + M1 独立 Checker 双通道）已采用（ADR-001），SFF 要求 ≥ 60%（Type B → Route 1H HFT=1）。

### 6.6 SFF 初步估算（v0.1 专家判断）

| 失效分类 | 估算条目 | FM-ID 列表 |
|---|---|---|
| λSD（安全，可检测） | 3 | FM-M7-02, FM-M7-10, FM-M7-19 |
| λSU（安全，不可检测） | 1 | FM-M7-17（缓冲区溢出 → 丢日志，不影响安全功能） |
| λDD（危险，可检测） | 5 | FM-M7-08, FM-M7-13, FM-M7-15, FM-M7-17 部分, FM-M7-20 部分 |
| λDU（危险，不可检测） | 9 | FM-M7-01, FM-M7-03, FM-M7-04, FM-M7-05, FM-M7-06, FM-M7-07, FM-M7-09, FM-M7-11, FM-M7-12, FM-M7-14, FM-M7-16, FM-M7-18, FM-M7-20 部分 |
| CCF | 1 | FM-M7-08/09（WatchdogMonitor 与主线程共因——同一进程内失效） |

**SFF 估算**：λSD + λSU + λDD / λtotal ≈ (3+1+5)/20 = **45%**（v0.1 专家判断）

> **Route 1H HFT=0 要求 ≥ 90%（Type B）**→ 本模块单独不满足。
> → **HFT=1 架构（M7 作为独立 Checker + M1 内 Checker）已采用（ADR-001）**，HFT=1 要求 ≥ 60%。
> → 当前估算 45% 接近 60%；**M7 作为 Checker 的 SFF 可能更高**，因为 Checker 路径中更多失效模式是 Safe Failure（宁可误报安全，不可漏报危险）。
> → 精确 SFF 在 HAZID RUN-001 (8/19) 后定量 FMEDA 计算。

### 6.7 M7 独有的失效模式分析（Checker 本身故障时无法自我检测的场景）

**核心问题**：M7 是 Checker——谁来检查 Checker？

**M7 Checker 自身故障的四层检测体系**：

| 层次 | 检测者 | 检测内容 | 检测周期 | DC 贡献 |
|---|---|---|---|---|
| **L1 内部自检** | M7 自身 | RAM CRC, ALU 测试向量, 控制流签名 | 100ms–1000ms | 90% |
| **L2 外部交叉监控** | X-axis Deterministic Checker | M7 心跳（1 Hz），M7 输出 Safety_AlertMsg 一致性 | 1000ms | 95% |
| **L3 M1 超时保护** | M1 ODD Manager | M7 消息超时（≤ 1500ms） | 1500ms | 99% |
| **L4 人工/ROC 监控** | M8 HMI + ROC 操作员 | M8 显示 "安全监督失效" 红色告警 | 实时 | < 60% |

**Checker 自身故障的典型场景**（FM-M7-11 详细展开）：

1. **Checker 逻辑错误但自检通过**（最危险场景）：
   - 缓解：X-axis Checker 作为外部独立 Checker 监控 M7 输出
   - 检测方法：M7 输出 Safety_AlertMsg 与 X-axis Checker 自身评估对比（如果 X-axis 也检测到同一场景但 M7 未告警 → M7 可能故障）
   - 注意：X-axis 与 M7 是分层互补而非冗余——两者检测条件不同

2. **Checker 静默失效（进程运行但不执行检查）**：
   - 缓解：约束执行计数器（HC-MON 每周期递增，独立 watchdog 线程监控计数器递增）
   - 如果计数器停滞 → M7 自身 watchdog 触发 → 系统降级

3. **Checker 阈值配置错误（所有约束阈值同时偏移）**：
   - 缓解：启动时阈值 CRC 校验 + 值域检查
   - 配置来源单一（`m7_params.yaml`）→ 配置文件 CRC 由 Capability Manifest 加载器校验

**设计原则**：M7 Checker 的故障检测覆盖率不可能达到 100%（自指问题）。但通过 L1–L4 四层检测 + Fail-Safe 设计（M7 故障 → 自动 D2 + MRM-01），系统整体安全性不受 M7 Checker 单点失效威胁。

## 8. MRM 命令链

### 8.1 命令链架构

```
M7 Checker（安全评估 + recommended_mrm 索引）
   │
   │ Safety_AlertMsg { recommended_mrm = "MRM-01"|"MRM-02"|"MRM-03"|"MRM-04" }
   ↓
M1 ODD Manager（仲裁：ODD 状态 × 系统健康态 → 决策是否执行 MRM）
   │
   │ MRM 命令分发（M1 → M5 TacticalPlanner）
   ↓
M5 TacticalPlanner（执行 MRM 预定义指令 + 参数从 Capability Manifest 读取）
```

**关键设计原则**（ADR-001 + MUST-9）：
- M7 **不直接向 M5 注入轨迹或命令**——所有 MRM 命令通过 M1 仲裁后下发
- M5 是唯一执行 MRM 预定义指令的 Doer 模块
- M7 仅输出 `recommended_mrm` 索引（枚举值），不输出具体执行参数
- 具体执行参数由 M5 从 Capability Manifest 读取（船型适配）
- **MUST-9 (FM-2)**：碰撞应急场景下，M5 发送 `safety_concern_event` 至 M7（而非直接下发 MRM），由 M7 唯一权限决策 MRM 执行

### 8.2 MRM 命令参数表（§11.6 锁定）

| 索引 | 命令 | 触发场景 | M7 HC 触发源 | 执行参数（初始设计值，HAZID 校准） |
|---|---|---|---|---|
| **MRM-01** | 减速至安全速度维持航向 | HC-2 / HC-3 / HC-4 / HC-5 / Watchdog 超时 / DC 不足 | 多源 | speed_target = 4 kn, decel_time ≤ 30 s |
| **MRM-02** | 停车（速度 → 0） | 连续 Checker 否决 / 多模块同时 CRITICAL | HC-3 (多模块) | thrust = 0, drift to stop |
| **MRM-03** | 紧急转向 | HC-1 / HC-6 | CPA 不一致 / ROT 超限 | heading_change = ±60°, rot = 0.8 × rot_max |
| **MRM-04** | 抛锚序列 | 系统失能（所有 Doer 同时失效） | Watchdog 全超时 | depth ≤ 30 m, speed ≤ 4 kn |

**工程依据**：详见表 §11.6（Yasukawa 2015 4-DOF MMG + COLREG Rule 8/17）。所有参数标注 [初始设计值，HAZID 校准]，FCB 实船试航后更新。

### 8.3 M7 → M1 Safety_AlertMsg 字段映射

```idl
# Safety_AlertMsg (发布者: M7, 订阅者: M1, 事件触发)

    timestamp    stamp;
```

## 9. Resume 时序

### 9.1 回切顺序化协议（§11.9.2 实装）

```
T0:        Hardware Override Arbiter → M1: OverrideActiveSignal { override_active=false }
T0+0 ms:   M1 接收信号 → "回切准备"状态
T0+10 ms:  M7 主仲裁线程启动：
           - SOTIF 假设违反检测重置 + 开始周期监控
           - 6 类硬约束重新激活
           - WatchdogMonitor 重置所有模块 loss_count
T0+10 ms:  M2 重新进入活跃状态（World_StateMsg 输出恢复）
T0+100 ms: M7 心跳确认 + 安全监控稳定（≥ 5 个连续周期无异常）→ 
           向 M1 发送 "M7_READY" 信号
T0+110 ms: M1 收到 M7_READY → 向 M5 发送 "M5_RESUME" 信号
T0+110 ms: M5 重新读取当前状态 + 重启 Mid-MPC（积分项重置）+ BC-MPC（积分项重置）
T0+120 ms: M5 输出第一个 AvoidancePlan（status = NORMAL）
T0+150 ms: ASDR 标记 "override_released" 事件 + 记录回切顺序时间戳
```

### 9.2 Resume 状态机

```cpp
enum class ResumeState : std::uint8_t {
  kIdle,              // 正常监控模式
  kOverrideActive,    // Override 激活中（M7 主仲裁暂停，降级监测线程活跃）
  kPreResumeCheck,    // T0+10ms → T0+100ms：M7 安全监控稳定检查
  kReady,             // M7_READY 已发送，等待 M5_RESUME
  kResumed,           // M5 已恢复输出 NORMAL
  kResumeTimeout,     // 超时（T0+100ms 内 M7 未 READY 或 T0+150ms M5 无输出）
};

class ResumeHandler {
public:
  void on_override_inactive(std::chrono::steady_clock::time_point t0) noexcept;
  void on_m7_stable(std::chrono::steady_clock::time_point now) noexcept;
  void on_m5_first_output(std::chrono::steady_clock::time_point now) noexcept;
  void on_resume_timeout() noexcept;

private:
  ResumeState state_{ResumeState::kIdle};
  std::chrono::steady_clock::time_point t0_;
  std::uint32_t stable_cycle_count_{0};  // M7 稳定周期计数（目标 ≥ 5）
  static constexpr std::uint32_t kStableCyclesRequired = 5;
  static constexpr auto kM7ReadyTimeout = std::chrono::milliseconds(100);
  static constexpr auto kM5OutputTimeout = std::chrono::milliseconds(150);
};
```

### 9.3 超时保护

| 超时条件 | 触发时间 | 系统响应 |
|---|---|---|
| M7 在 T0+100ms 内未发出 READY | T0+100ms | M1 自动切换到 D2 + 触发 MRM-01 |
| M5 在 T0+150ms 内未输出 NORMAL | T0+150ms | M1 自动切换到 D2 + 触发 MRM-01 |
| M7 READY 发送后 M5 在 50ms 内无响应 | M7_READY + 50ms | M7 重新评估 → 可能需要重新发送 M7_READY |

### 9.4 接管期间降级监测线程（§11.9.1）

M7 接管期间的降级监测线程（4 项）不依赖 M7 主仲裁——即使 M7 主仲裁暂停，降级监测仍通过 M8 实时显示（< 100ms 时延）：

| 监测项 | 触发条件 | 响应 |
|---|---|---|
| 通信链路中断 | RTT > 2s 持续 5s 或丢包 > 50% | M8 红色降级告警标志 |
| 传感器降质 | Multimodal Fusion 报 DEGRADED 状态 | M8 降级告警 + 提示 ROC |
| 新威胁出现 | M2 新增 CPA < 阈值目标 | M8 新威胁告警 |
| M7 自身异常 | M7 心跳丢失 / 监测线程异常 | M8 "安全监督失效" 红色告警 |

M7 不单独满足 SIL 2 HFT=0 的 SFF ≥ 90% 要求（Type B）。但 ADR-001 已采用 **HFT=1 双通道架构**：

- **CFF 抑制**：M7 与 M1 不共享代码/库/数据结构（ADR-001 Doer-Checker 独立性约束）

这满足 IEC 61508-2 Table 3 HFT=1 要求（Type B SFF ≥ 60%）。

## 12. 需探讨的设计决策

### 12.1 6 类硬约束的独立执行线程结构 vs 单循环

**已决策：方案 C（混合架构）**— 见 §4.8。

**理由摘要**：
- 关键约束（HC-1/2/5/6）事件驱动（< 2ms）
- 周期约束（HC-3/4）定时器驱动（< 5ms）
- 全部运行在 MutuallyExclusive callback group → 无并发问题
- 最坏延迟 < 8ms << 10ms ✅

### 12.2 代码结构实现 LOC ≥ 50:1

**M7 代码上限**：≤ 800 LOC（见 §5.2 分解）。

**硬性保证**：
- LineThreshold = 40（每源文件最大 40 行）
- 禁止模板、禁止虚函数、禁止异常
- 单函数单职责
- CODEOWNERS 双重 review

**软性保证**：
- CI 自动度量（每 commit）
- AI Slop Remover 审查

### 12.3 SBOM ∩ = ∅ 验证脚本的具体实现

**已决策**：四层验证（L1 源码 → L2 构建 → L3 包管理 → L4 SBOM），见 §5.4。

**技术栈**：
- **apt**：`dpkg -l` 检查系统包
- **pip**：`pip list` 检查 Python 包（M7 不应依赖 Python）
- **conan**：`conanfile.txt` 检查（M7 应纯 CMake）
- **syft**：生成 CycloneDX SBOM + `jq` 比较

### 12.4 FMEDA M7 表中 M7 独有的失效模式

**核心问题**：Checker 本身故障时无法自我检测——见 §6.7。

**四层检测体系**：
1. M7 内部自检（RAM CRC, ALU 测试向量, 控制流签名）
2. X-axis Checker 外部交叉监控
3. M1 超时保护
4. M8 HMI + ROC 人工监控

**最危险场景**（FM-M7-11）：Checker 逻辑错误但自检通过 → 由 X-axis Checker 外部监控补充。

### 12.5 Watchdog 3-miss 阈值的合理性

**已分析**：见 §4.4 合理性论证表。

**结论**：
- 架构初始值—FCB 实船试航后 HAZID 校准
- 最坏响应时间（900ms for M2）< 安全时间窗（1.2s）
- 误报概率可忽略
- HAZID RUN-001 (8/19) 将提供精确的 DDS 通信可靠性数据用于校准
